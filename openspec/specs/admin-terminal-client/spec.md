# admin-terminal-client Specification

## Purpose

Определяет безопасный приватный терминальный интерфейс, через который уполномоченные операторы просматривают контекст жалоб и выполняют проверяемые действия модерации Bord.

## Requirements

### Requirement: Отдельный административный клиент
Система SHALL предоставлять отдельный terminal-клиент для административных задач, подключаемый к management API независимо от публичного пользовательского клиента.

#### Scenario: Запуск с доступным management API
- **WHEN** оператор запускает admin-клиент с адресом приватного management API и действительным credential
- **THEN** клиент открывает очередь жалоб и не требует включения административного режима в обычном клиенте Bord

#### Scenario: Management API недоступен публично
- **WHEN** внешний клиент запрашивает административный маршрут через публичный listener Bord
- **THEN** сервер возвращает отсутствие маршрута и не раскрывает административные данные

### Requirement: Защищенная загрузка credential
Admin-клиент MUST принимать credential из переменной окружения или защищенного файла и MUST не принимать секрет непосредственно в аргументе командной строки или сохранять его в обычном состоянии TUI.

#### Scenario: Файл credential доступен другим пользователям
- **WHEN** оператор указывает файл credential с небезопасными правами доступа на поддерживаемой POSIX-платформе
- **THEN** клиент отказывается использовать файл и выводит безопасную диагностику без содержимого credential

#### Scenario: Ошибка аутентификации
- **WHEN** management API отклоняет истекший или отозванный credential
- **THEN** клиент показывает состояние неавторизованного доступа без отображения или журналирования credential

### Requirement: Очередь жалоб
Admin-клиент SHALL отображать постраничную очередь жалоб с причиной, временем, идентификатором поста и признаком наличия следующей страницы.

#### Scenario: Открытие очереди
- **WHEN** роль оператора допускает просмотр жалоб
- **THEN** клиент загружает первую страницу, позволяет выбрать жалобу клавиатурой или мышью и предоставляет явное обновление списка

#### Scenario: Следующая страница
- **WHEN** оператор достигает конца страницы с непустым курсором продолжения
- **THEN** клиент загружает следующую страницу без потери уже показанных элементов и без дубликатов

### Requirement: Контекст модерируемого поста
Management API SHALL возвращать уполномоченному оператору контекст выбранного поста: доску, тред, соседние публикации, состояние видимости и метаданные вложения, но MUST не включать исходный IP.

#### Scenario: Просмотр скрытого поста
- **WHEN** модератор открывает жалобу на скрытый пост
- **THEN** admin-клиент показывает сохраненный модерируемый текст и метаданные вложения с явной отметкой скрытого состояния

#### Scenario: Обычный просмотр контекста
- **WHEN** оператор просматривает контекст поста без выполнения операции раскрытия IP
- **THEN** ответ не содержит исходный IP, зашифрованный IP или credential автора

### Requirement: Модерация с обязательной причиной
Admin-клиент SHALL позволять уполномоченному модератору скрыть или восстановить пост и закрыть тред только после ввода допустимой причины и явного подтверждения.

#### Scenario: Подтвержденное скрытие
- **WHEN** модератор вводит допустимую причину и подтверждает скрытие видимого поста
- **THEN** клиент выполняет одну операцию, показывает результат и обновляет контекст до фактического серверного состояния

#### Scenario: Недостаточная роль
- **WHEN** оператор пытается выполнить действие, не разрешенное его ролью
- **THEN** сервер отклоняет действие, а клиент сохраняет текущий контекст и показывает отказ без ложного успешного состояния

#### Scenario: Пустая причина
- **WHEN** оператор пытается подтвердить действие без допустимой причины
- **THEN** клиент не отправляет административный запрос и оставляет форму открытой с объяснением ошибки

### Requirement: Управление блокировками
Admin-клиент SHALL отображать активные и недавно отозванные или истекшие блокировки и позволять уполномоченному модератору создавать и отзывать их с причиной.

#### Scenario: Создание блокировки из поста
- **WHEN** модератор выбирает поддерживаемые операции, срок и основание для субъекта выбранного поста
- **THEN** сервер создает ограниченную по сроку блокировку, клиент показывает ее идентификатор и обновляет список блокировок

#### Scenario: Отзыв блокировки
- **WHEN** модератор подтверждает отзыв активной блокировки с допустимой причиной
- **THEN** блокировка помечается отозванной, перестает применяться и остается доступной в истории

### Requirement: Просмотр аудита
Admin-клиент SHALL предоставлять постраничный read-only список административных действий с субъектом, действием, целью, причиной, временем и результатом без секретов и исходных IP.

#### Scenario: Просмотр неуспешного действия
- **WHEN** оператор открывает аудит после отклоненной административной операции
- **THEN** запись показывает неуспешный результат и безопасный код ошибки, но не credential и не чувствительное содержимое запроса

### Requirement: Контролируемое раскрытие IP
Только роль administrator SHALL иметь возможность запросить исходный IP выбранного поста после отдельного предупреждения, ввода причины и явного подтверждения.

#### Scenario: Разрешенное раскрытие
- **WHEN** administrator подтверждает раскрытие IP с допустимой причиной
- **THEN** клиент показывает IP только в текущем защищенном представлении, а сервер записывает отдельное аудируемое действие

#### Scenario: Раскрытие модератором
- **WHEN** credential роли moderator запрашивает раскрытие IP
- **THEN** сервер отклоняет запрос, а клиент не показывает никаких данных, из которых можно восстановить IP

### Requirement: Согласованное терминальное управление
Admin-клиент SHALL поддерживать адаптивную компоновку, темы, навигацию клавиатурой и кликабельные команды мыши в терминалах, поддерживаемых обычным Bord TUI.

#### Scenario: Узкий терминал
- **WHEN** ширины терминала недостаточно для одновременного отображения списка и контекста
- **THEN** клиент показывает одну активную панель и позволяет переключать панели без потери выбора и введенной причины

#### Scenario: Клик по административной команде
- **WHEN** оператор нажимает мышью видимую команду нижней панели
- **THEN** выполняется та же операция, что и для указанной рядом горячей клавиши

### Requirement: Дистрибуция admin-клиента
Релиз Bord SHALL предоставлять admin-клиент для Linux, macOS и современного Windows Terminal вместе с документацией безопасного приватного подключения.

#### Scenario: Проверка release-архива
- **WHEN** оператор скачивает архив admin-клиента для поддерживаемой платформы
- **THEN** архив содержит бинарник, руководство, LICENSE и THIRD_PARTY_NOTICES и проходит опубликованную SHA-256 проверку
