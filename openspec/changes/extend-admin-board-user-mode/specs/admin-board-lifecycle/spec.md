# Spec Delta

## Purpose

Определяет безопасное управление жизненным циклом досок через приватную административную поверхность без физического удаления пользовательского контента.

## ADDED Requirements

### Requirement: Management-only список досок
Система SHALL предоставлять administrator постраничный список активных и архивных досок с идентификатором, slug, названием, состоянием и безопасными счетчиками контента.

#### Scenario: Просмотр всех досок
- **WHEN** administrator открывает экран управления досками
- **THEN** клиент показывает активные и архивные доски, не обращаясь к публичному каталогу

#### Scenario: Маршрут недоступен публично
- **WHEN** внешний клиент запрашивает список административных досок через public listener
- **THEN** сервер возвращает `404` и не раскрывает архивные доски

#### Scenario: Недостаточная роль
- **WHEN** credential роли moderator или reports запрашивает управление досками
- **THEN** сервер возвращает запрет доступа без изменения данных

### Requirement: Создание доски
Система SHALL позволять administrator создать активную доску с допустимыми уникальными slug и названием, обязательной причиной и аудируемым результатом.

#### Scenario: Успешное создание
- **WHEN** administrator подтверждает создание доски с допустимыми slug, названием и причиной
- **THEN** доска появляется в management-списке и публичном каталоге, а аудит содержит успешное действие без credential

#### Scenario: Конфликт slug
- **WHEN** administrator пытается создать доску со slug существующей активной или архивной доски
- **THEN** сервер возвращает conflict и не создает вторую доску

#### Scenario: Невалидные поля
- **WHEN** slug, название или причина не соответствуют серверным ограничениям
- **THEN** клиент оставляет форму открытой, а сервер не изменяет данные

### Requirement: Архивирование без удаления
Система MUST архивировать доску изменением ее состояния и MUST сохранять связанные треды, посты, вложения, жалобы и audit history.

#### Scenario: Подтвержденное архивирование
- **WHEN** administrator вводит допустимую причину и повторно подтверждает архивирование активной доски
- **THEN** доска становится архивной, исчезает из публичных списков и остается в management-списке

#### Scenario: Публичное чтение архивной доски
- **WHEN** пользователь обращается к каталогу, треду, постам или вложению, принадлежащему архивной доске
- **THEN** public API отвечает так, как для отсутствующего ресурса, не раскрывая факт архивирования

#### Scenario: Новая запись в архивную доску
- **WHEN** пользователь пытается создать тред или ответ в архивной доске
- **THEN** сервер отклоняет запись и не создает пост, вложение-связь или событие

#### Scenario: Данные сохранены
- **WHEN** administrator просматривает архивную доску через management API
- **THEN** существующий контент и moderation context остаются доступными и неизменными

### Requirement: Восстановление архивной доски
Система SHALL позволять administrator восстановить архивную доску после ввода причины и явного повторного подтверждения.

#### Scenario: Успешное восстановление
- **WHEN** administrator подтверждает восстановление архивной доски
- **THEN** доска снова появляется в публичном каталоге и принимает новые записи

#### Scenario: Повтор состояния
- **WHEN** administrator архивирует уже архивную доску или восстанавливает активную
- **THEN** сервер возвращает conflict, сохраняет текущее состояние и записывает неуспешный audit result

### Requirement: Аудит управления досками
Каждая попытка create, archive и restore SHALL записывать actor, действие, target, причину, outcome и request ID без credential и пользовательского содержимого.

#### Scenario: Неуспешное административное действие
- **WHEN** операция управления доской отклонена валидацией, ролью или конфликтом состояния
- **THEN** audit показывает безопасный error code и не содержит bearer, request body или исходный IP
