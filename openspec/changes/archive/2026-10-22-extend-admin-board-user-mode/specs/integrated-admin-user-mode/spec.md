# Spec Delta

## Purpose

Определяет безопасное переключение между административной работой и полноценным пользовательским опытом Bord в одном terminal-клиенте.

## ADDED Requirements

### Requirement: Полноценный пользовательский режим
`bord-admin` SHALL предоставлять режим «Пользователь» с теми же публичными досками, тредами, публикацией, ответами, удалением своих постов, вложениями и SSE-обновлениями, что отдельный клиент `bord`.

#### Scenario: Переход в пользовательский режим
- **WHEN** оператор выбирает «Пользователь» в верхнем меню клавиатурой или мышью
- **THEN** интерфейс показывает обычный Bord TUI и загружает данные через настроенный public API

#### Scenario: Публикация как пользователь
- **WHEN** оператор создает тред или ответ в пользовательском режиме
- **THEN** запрос использует обычную анонимную user session и не получает административных полномочий

#### Scenario: Возврат в административный режим
- **WHEN** оператор выбирает «Администрирование»
- **THEN** клиент возвращает сохраненные admin screen, selection и pagination state без повторной передачи credential в public API

### Requirement: Разделение public и management transport
Клиент MUST использовать отдельные base URL и HTTP clients для public и management API и MUST добавлять bearer credential только к management requests.

#### Scenario: Проверка public запроса
- **WHEN** пользовательский режим выполняет любой HTTP или SSE запрос
- **THEN** запрос не содержит management Authorization header или значение credential

#### Scenario: Public API недоступен
- **WHEN** management API доступен, но public API временно недоступен
- **THEN** административный режим продолжает работать, а пользовательский режим показывает безопасную retryable ошибку

#### Scenario: Настройка public URL
- **WHEN** оператор задает `--server` или `BORD_SERVER`
- **THEN** значение применяется только к пользовательскому режиму и сохраняется отдельно от management URL

### Requirement: Разделенное локальное состояние
Admin-клиент MUST хранить anonymous user session/delete capabilities в обычном защищенном user state и MUST не смешивать их с management credential или admin state.

#### Scenario: Сохранение состояния после переключений
- **WHEN** оператор переключался между режимами и корректно завершил клиент
- **THEN** тема и последний режим сохраняются в admin state, а user session, delete secrets и последняя доска сохраняются в обычном user state

#### Scenario: Проверка serialized state
- **WHEN** локальные state-файлы проверяются после работы
- **THEN** ни один из них не содержит management bearer, а admin state не содержит user delete secrets

### Requirement: Общий верхний переключатель режимов
Верхняя строка SHALL показывать кликабельные пункты «Пользователь» и «Администрирование» и обеспечивать одинаковый переход по клавиатуре во всех размерах терминала.

#### Scenario: Переключение мышью
- **WHEN** оператор нажимает видимый пункт режима
- **THEN** выполняется тот же переход, что у указанной горячей клавиши, без активации элемента контента под верхней строкой

#### Scenario: Узкий терминал
- **WHEN** ширины недостаточно для всех пунктов верхнего меню
- **THEN** активный режим и команда переключения остаются доступны без повреждения рамок или рабочей области

### Requirement: Рамки как в обычном Bord
Административный интерфейс SHALL использовать те же shared chrome, line set, размеры рамок, стыки панелей, active-border styling и narrow layout rules, что обычный Bord.

#### Scenario: Две панели на широком экране
- **WHEN** экран жалоб показан в широком терминале
- **THEN** список и контекст имеют выровненные углы, высоту и разделитель по тем же правилам, что панели обычного Bord

#### Scenario: Modal и одиночная панель
- **WHEN** открыта административная modal или узкая компоновка
- **THEN** рамка не содержит разрывов, наложений, лишних вертикальных линий или строк шире терминала

#### Scenario: Смена темы и MC skin
- **WHEN** оператор меняет встроенную тему или MC skin в любом режиме
- **THEN** оба режима используют одну выбранную палитру и одинаковый набор символов рамки

### Requirement: Единая модалка выбора темы
`bord-admin` SHALL использовать тот же shared рамочный theme picker, каталог тем и правила взаимодействия, что обычный Bord TUI, вместо отдельной административной реализации списка тем.

#### Scenario: Открытие выбора темы
- **WHEN** оператор нажимает `F2`, `t` вне текстового ввода или пункт «Тема» мышью
- **THEN** поверх текущего режима открывается рамочный список встроенных тем и найденных MC skins с текущей темой в фокусе

#### Scenario: Навигация по длинному списку
- **WHEN** список тем выше доступной области терминала
- **THEN** `↑/↓`, `j/k`, `PgUp/PgDn` и колесо мыши прокручивают ограниченное окно списка без выхода за границы экрана

#### Scenario: Выбор темы
- **WHEN** оператор нажимает `Enter` или кликает по видимой теме
- **THEN** picker закрывается, выбранная тема применяется к обоим режимам и сохраняется в admin state

#### Scenario: Отмена выбора
- **WHEN** оператор нажимает `Esc`, повторно `F2`/`t` или кликает вне picker
- **THEN** picker закрывается без изменения ранее выбранной темы

#### Scenario: Малый терминал и небезопасное имя
- **WHEN** picker открыт в малом терминале или название MC skin содержит управляющие последовательности
- **THEN** picker остается в пределах экрана, безопасно сокращает очищенное название и не повреждает underlying layout
