# Демо-данные для ручного тестирования

`bord-server demo-seed` явно и однократно наполняет локальную SQLite-базу
детерминированными mock-данными. Команда никогда не запускается из `serve`, не
имеет production-путей по умолчанию и требует подтверждение.

```sh
go run ./cmd/bord-server demo-seed \
  --database /tmp/bord-demo.db \
  --blobs /tmp/bord-demo-blobs \
  --confirm DEMO-SEED
```

После этого сервер можно запустить с конфигурацией, указывающей те же
`storage.database` и `storage.blobs`. В данных есть разделы `general`, `tech`,
`games`, `meta`, несколько поднятых тредов, ответы и reply-ссылки, разные
авторы и даты, русский/английский/Unicode-текст, tombstone и закрытый тред.
Небольшие значения `limit` удобны для проверки прокрутки каталога и треда.

Повтор той же команды безопасен: fixture проверяется и возвращается
`"replayed": true`, новые строки не создаются. Если зарезервированные ID или
slug уже заняты другими данными либо fixture был изменён, команда завершится
ошибкой и ничего не перезапишет. Реальные IP, учётные данные и секреты в
fixture отсутствуют; `--blobs` всё равно обязателен, чтобы проверить настоящий
путь blob storage.

Для пересоздания неизменённого fixture требуется отдельное усиленное
подтверждение:

```sh
go run ./cmd/bord-server demo-seed \
  --database /tmp/bord-demo.db \
  --blobs /tmp/bord-demo-blobs \
  --reset --force --confirm RESET-DEMO-SEED
```

Reset удаляет только детерминированные demo-ID и принадлежащие fixture
delete-токены и outbox-события. Записи request subject сохраняются и теряют
ссылку на пересозданный пост; если для demo-поста уже создан report, reset
откажется удалять операторские или пользовательские данные. Он не очищает
произвольную базу и отказывается работать с изменённым fixture. Для
production/staging используйте обычные миграции и операторские процедуры, а не
эту команду.
